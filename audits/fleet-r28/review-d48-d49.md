## §2 THE ATTACK ON D48 (the marker model)

**F1 — STRONG: `notes` has the same "no OT home" hole the ruling cites to reject `keyword` — "zero OT change" is only true for `duration`.**
The rejection argument (research §4a, adopted): keyword would make "the spec define a field its own SSOT cannot round-trip — the exact D2e-class hole the bridge field-law exists to prevent" (D2e = the engine-owned vs sidecar-owned field law, 09:15). Now count OT's text homes: `Bookmark` has exactly **one** — `note` (types/index.ts:32) — and the bridge already spends it on **`label`** (sceneBridge.ts:377 forward, :559 backward). Marker v2 has **two** text fields (`label?` + `notes?`). One of them cannot round-trip through the SSOT without an OT widening or a packing convention. The ruling's decisive-evidence sentence ("OT's own `Bookmark {time, note?, color?, duration?}` already carry the range semantic — the flat spec Marker is narrower than its own SSOT") is true for `duration`, **half-true for `notes`** (narrower yes, round-trippable only by evicting `label`). Severity: lower than keyword (a home exists for one of the two), but the ruling's "Zero OT change" headline is wrong as stated and the r5 port will re-open the exact hole D48 just closed. **Fix (amendment 1):** state the disposition — recommended: OT's `note` carries `notes` (the long-form; the reference dialog's Notes is the payload the DTD `note` attr wants, 10:591) and `label` becomes doc-side (the bridge synthesizes it like `id` today), **or** `Bookmark` gains `label?` at the r5 port — either way register it.

**F2 — STRONG: spec 10 is missing from the amendment map — and §4.7 is already stale on TWO axes D48 touches.**
D48's 9 sites: 09×3, 05, 16, 18×2, 15, register. Spec 10 — the **export** consumer of the marker model — is absent. Live state: §4.7's `buildMarkers` reads `ctx.project.markers` (:596/:602) — the **project-level array that A2 retired in R15** (09:77-78) — a latent break independent of D48; and it emits only `start` + `value=label` (:607-609) while FCPXML's own `<marker>` DTD carries `duration` (`:588`) and `note` (`:591`) — the exact two fields D48 adopts. Whatever the export posture (map them, or the honest "not exported v1" limitation row), the D48 pass is the one touch that should sweep the stale project-markers read. **Fix (amendment 2):** add a 10th site — 10 §4.7: fix the per-scene read + one row for duration/note (mapped or registered-not-exported).

**F3 — the SCENE-RESIZE silence (a real WYSIWYG-visible semantic left unruled).**
The range law "end = time + duration, ≥1 frame, ≤ scene duration" is a **write-time** invariant (the mock enforces exactly that, useUiStore.ts:1534-1549). The mock: markers beyond the new end are **kept** — only the playhead is reconciled on scene switch (:1320-1324); no re-clamp sweep exists anywhere in the store (grep-verified). Keep vs clamp vs prune is visible (the ruler's band vs the scene extent) and unruled. **Fix (amendment 3):** one sentence in 05 §11.1 — recommend adopting the mock's keep-law (authored data is kept, display-clamped; the write path re-clamps) as the registered v1 semantics.

**F4 — ⇧M's range reading is unruled.**
`removeMarkersAt` matches only the marker **start** (±1 frame, useUiStore.ts:1987). A playhead **inside** mk-5's 17→24 range deletes nothing. 16 §3.7's "Delete marker at playhead" (and 15's `deleteMarker{time}`-era semantics) needs the range reading stated (start-match only, as the mock — or span-contains). **Fix (amendment 4):** one clause in the 16 §3.7 edit (site 5 already touches that file).

**F5 — "keyword REJECTED": UPHELD.** "No consumer" verified by grep: keyword lives only in the inspector field (MarkerInspector.tsx:136-146), the store patch (:1543/:1553), fixtures (mk-3 'music'), and 3 direct test pins (MarkerInspector.test:21/:53-62, useUiStore.test:2166, mockData.test:129) — nothing downstream (search/filter/export/nav) consumes it. The clip-marker case is **stronger** than C35: the field alone corrupts offsets on split/trim (the mock's re-offset law bundle is insertPlan.ts:213-229/:243/:444 — trim filter+shift, split partition), and the plan already phase-tags "marker v2 … at r5-entry" (IMPLEMENTATION-PLAN:25).
