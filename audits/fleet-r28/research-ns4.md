## 2. The candidate architectures

**(a) The bridge adapter** — the junction formalized/extended for GPU: a PURE SceneTracks→render-plan translator in the bridge family (the visual twin of scene-to-segments), feeding the venue stack's existing input surface. Two sub-variants:
- **(a1) plan-level:** the adapter emits the layer/plan list consumed at the compositor edge (CompositeLayer-shaped) — the venue's scene-assembly bypassed.
- **(a2) IR-level (the projector):** the adapter mints the venue IR — `project(scene) → TimelineData` (D12 clause 1's own words, `00-master-spec.md:328`) — feeding `setTimeline`/scene-assembly whole; the venue stack reused unchanged (cache invalidation = array identity, `scene-assembly.ts:17-24`).

**(b) Venue-native** — the GPU render path lives inside the engine's venue model directly, SceneTracks consumed closer to the GPU: the compositor/scene-assembly grows a SceneTracks input contract (NS-4's second option, "a new compositor input contract over SceneTracks"; the OpenCut-classic lineage — its `scene-builder.ts` walks SceneTracks natively, `07:990-991`).

**(c) Hybrid** — adapter for edit-preview + venue-native for export (or the today-shaped split: Canvas2D consumer preview + engine-native GPU for the app only).

## 3. Analysis against the constraints

**D12's freeze (the junction one-directional; venue-internal frozen).** Option (b) makes the venue SceneTracks-aware: the ticks law, retime clamps, transition descriptors, z-order/visibility semantics — the bridge's twin-pinned translation laws (`composition-frame.ts:39-56`, `:319-349`; opencut-laws value-imports, engine DECISIONS.md:547-561) — would be re-implemented venue-side. That is a second visual-semantics home, exactly the dual-home D12 clause 3 killed on the editing side (`00-master-spec.md:330`; the R9 supersession of Decision 11's "two algorithm homes", `:300-314`). It also violates spec 07's own renderer law — "the renderer doesn't know about SceneState" (`07:91`). Option (a) keeps the venue model-blind and the junction one-way: SceneTracks stops at the bridge, the venue IR is a derived cache ("never an editing input", `00:328`). **(a) wins.**

**The 46 rgba8unorm sites.** Under (a2), the upgrade is a bounded venue-internal refactor: all 46 sites/10 files are engine-internal modules (verified §1.4); the junction passes descriptors/params — never texture formats — so the float-working-texture upgrade (08's r3 binding row, `08:22`) has **zero junction surface**. The parity corpus (adapter vs the engine-native oracle on shared fixtures) is format-blind by construction (both sides read the same post-render pixels). Under (b), the SceneTracks ingestion layer would have to land SIMULTANEOUSLY with the format upgrade inside the same modules — a wider blast radius and a new un-pinned seam crossing the color binding. **(a) is cheaper and safer; the upgrade's home stays the venue stack.**

**The r3 color venue table (fragment passes on rgba16float).** The venue law anchors the grade passes "between composite and display transfer" over the working texture (`08:26`; `04:109-175` §4's chain; §5.2's rgba16float override `:517-523`). Those anchors are the venue pipeline's OWN stages. Option (a) hosts the table unchanged — composite, grade passes, display transfer all venue-internal, fed by the projected IR. Option (b) would re-host the table's anchor points around a SceneTracks-native compositor, re-opening an R27-ruled table. **(a) preserves the r3 entry artifact as ruled.**

**Realtime preview vs export (NS-1's coupling).** The venue's single `_buildLayers` path serves both preview and export (`player.ts:1297-1322`, `orchestrator.ts:15-16`) — the WYSIWYG law's code base (`04:671-694`). Under (a), the adapter is a pure function of (scene, t) — clock-agnostic; NS-1's clock question stays confined to the transport layer where it is filed (the engine Clock truth + imperative mirror + commit-on-pause, D16's law, `00-master-spec.md:376`). Under (c) (the hybrid), preview and export would fork render paths — preview ≠ export pixels, breaking 04 §9 and the one-path property the export orchestrator already consumes. **(c) rejected on WYSIWYG grounds.**

**The parity-twin role (the offline renderer pins r1).** The engine Timeline is "the offline reference implementation + the parity twin that pins the eventual r1 port" (engine DECISIONS.md:541-542); the r1 ports land in OT's ops layer with the engine methods as algorithm sources (`IMPLEMENTATION-PLAN.md:8`). Under (a2), the projected TimelineData and the engine-native authored Timeline are the SAME shape — the twin's oracle role extends for free to the projector corpus (spec 07's open row already names it: "S4 parity suite green **vs the engine Timeline oracle**", `07:19`). Under (b), TimelineData is demoted to an implementation detail and the twin loses its comparable shape. **(a2) keeps the twin honest.**

**The WDC DSP interplay (audio's separate venue).** Audio already runs the adapter architecture end-to-end: SceneTracks → scene-to-segments → SegmentStripAdapter → strips on WDC engine handles, one topology for realtime+offline ("the one-engine law", `scene-mixer.ts:8-10`). Choosing (a) for the visual path makes the two venues SYMMETRIC — one junction discipline, one bridge family, one projection law — and NS-5's edit-classification seam then serves both venues at one point (which edits change the projected visual plan / the audio segment set — today two glues, one seam). Choosing (b) would make the visual venue the lone SceneTracks-native exception in an otherwise adapter-shaped assembly.

**Sub-variant (a1) vs (a2).** (a1) would re-implement scene-assembly's plan walk bridge-side (transition windows, occlusion, transforms, video grouping) — duplicating venue-internal laws OUTSIDE the venue, the mirror image of (b)'s defect, and discarding the proven machinery the r3 binding is scheduled to land on. (a2) reuses the whole frozen stack, including its cache invalidation (plan keyed on array identity, `scene-assembly.ts:17-24`) which NS-5's re-project/reschedule classes plug into directly. **(a2) is the ruled sub-variant.** The spec-level contract name remains 07's FrameDescriptor (the corrected venue aligns its plan stage to that shape per 04 §7); the engine's venue-internal realization today is the projected TimelineData over scene-assembly.

**What stays Canvas2D:** the composition-frame consumer preview (the honest CSS-subset, D29.5c/D29.5d — `04:24-25`, `08:24`) stays as the consumer-viewer v1 AND the jsdom-pinnable pure-math oracle for the parity corpus; the GPU path is the fidelity+export tier it was always honest-skipping toward (`composition-frame.ts:88-91`).
