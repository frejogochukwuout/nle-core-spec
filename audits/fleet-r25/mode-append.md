## 3. SPEC-FIRST DESIGN ANALYSIS (the new §5.9A family for spec 06)

The proposal is a **placement-level composite family**, not an engine port: append = *resolve a time + place clips*, fully expressible over OT's existing ops layer (the one algorithm home, Decision 12.3) — unlike insert-edit-3-point, nothing here needs the engine's splice machinery. New subsection **06 §5.9A "Append at end"** (or the C45-recommended "edit functions" enumeration inside §5.9), with these five laws:

### (a) Contract

1. **resolve-append-point — PER-TRACK, not timeline-content-end.** `t₀ = max(0, max over target-track elements of (startTime + duration))`; empty track ⇒ 0. Recommendation: **per-track last-element-end**, justified: (i) **both** in-corpus implementations chose it (variants `insertPlan.ts:413-414`, mini `:1055`) — the corpus has already voted; (ii) the mock's own grammar is lane-local (ghost after Surf *on the lane*, `:311-318`); (iii) it is the only reading under which append **never creates a gap on the target track** — timeline-content-end (OT's `calculateTotalDuration`, `element-utils.ts:71-91`) would pad every shorter track with a leading gap, breaking the mode's contiguity intuition ("after the last edit", not "after the longest track's last edit"); (iv) it composes with the mini's bound-track law (kind→lane, D3.2) and the main-track zero-anchor (an append point is always ≥ the earliest element, so `enforceMainTrackStart` never rewrites it — 05 §14.5A). The r20 doc's open "align decision" (`:288`/`:389`) is hereby resolved **per-track**; note the linked-pair caveat in (b)3.
2. **multi-append ordering — pool display order, sequential accumulation.** `t_{i+1} = t_i + dur_i` — append points evolve *inside* the op (never pre-computed as N × the same t₀). Order source: the **pool's canonical display order filtered by the selection** — exactly OT's existing batch pattern (`page.tsx:521-523`, `LIBRARY_ASSETS.filter(selectedAssets.has)`), deterministic without upgrading the Set-based selection model to click-order. Duration per clip = the source's trimmed range (in/out honored, the 3-point shape — `useUiStore.ts:1303-1305`).
3. **playhead-ignored law.** The op reads neither `currentTime` nor any pointer-derived time; it does not move the playhead either. This is the mode's identity sentence ("regardless of where the playhead is located") and the mock's visual point (playhead drawn elsewhere, `:600`). Battery-pinnable: mid-timeline playhead ⇒ identical landing.
4. **No-push law.** Append is NOT `insert {ripple:true}`: nothing downstream moves (nothing is downstream), the ripple parameter is inapplicable (fixed false *by law*, not by default), and the grammar forbids the right-arrow token (r20 `:125`). Append ≠ the mini's gap-*fit* insert (which hunts interior gaps, OT-SEAMS row 5) — **append is always the tail**, never a gap fill.

### (b) Algorithm — composing existing primitives

1. **Single append** = `insertElement {element, strategy:'explicit', trackId, startTimeTicks: t₀}` — OT's existing verb, unchanged, with the append point resolved at the caller… **or the resolver** (see (c)). The overlap guard is satisfied *by construction* (t₀ ≥ every element end on that track) except the locked-track gate (TRACK_LOCKED refusal — the S2 law, already wired `api.ts:570-578`).
2. **Multi-append** = ONE `insertElements({elements, startTime: t₀, strategy:'explicit', trackId})` — the existing homogeneous-batch primitive already lands the first element at `startTime` and later elements at their **relative offsets** (`timeline-core.ts:886-911`), with the intra-batch overlap guard (`:922-929`) trivially satisfied when the client builds 0-based accumulated offsets; **ONE history entry** (`withUndo`, `:979-990`) — the one-entry law for free. **Caveat:** F1A-3 rejects heterogeneous batches (`:880-885`) — a mixed video+audio pool selection appends as **two kind-split batches** (one per target lane), still one history entry each, or one entry total inside the new op. This is the one primitive-composition seam the verb must rule.
3. **Linked audio — the linked-append law (recommendation: YES, the pair lands together, synced).** Does video-append auto-append audio to the paired track? In-corpus today: engine wire `addClip` **does** (linked audio companion, `api.ts:660-665`, freecut `headless/edit.ts:442-534`); OT insert does **not** (caller supplies elements — the pool batch sends video-only, `isSourceAudioEnabled` is a field, not a companion); variants append does **not** (single element, no `linkedTo` on the append path); mini has no linked model. **Recommended law:** a video source with audio appends the **A/V pair at the SAME startTime = the video track's append point**, companion on the paired audio track — sync by construction; the companion is *not* placed at the audio track's own content end (that desyncs whenever the tracks' tails diverge). Conflict case: existing audio content at/after that point ⇒ **the whole append refuses atomically** (reject-not-shift — 05 §14.5's normative policy + 00-master `:804`'s no-overlap invariant), never a partial pair. Justification: the engine's addClip is the corpus's only linked-append precedent; DaVinci appends A/V pairs; the corpus's honest-refusal law beats silent overlap. (In practice paired tracks' tails coincide, so the refusal is rare — but the law must exist because per-track resolution *creates* the divergence case.)
4. **Locked/unbound tracks** refuse honestly (mini `:1042-1050`; variants `insertPlan.test.ts:301-305`); PR69 C15's quantize-up never-below-tail guard is absorbed as a **frame-quantization detail** (snap law, 06 §5.16), not a new family member.

### (c) Wire verb (spec 15)

**Recommendation: canonical = `InsertCommand` gains a 6th placement strategy `{ type: 'append'; trackId?: string }`** (server-side time resolution; `trackId` optional with kind-routing default), and the multi form rides the **already-endorsed r1-adjacent `timeline.insertBatch` row (15 `:4908`, D29 F8)** as `insertBatch {elements[], placement:'append'}` — **one history entry, append points resolved inside the apply**. An OT-side convenience verb `timeline.append` may exist as a **documented wrapper**, exactly like `timeline.rippleDelete` (15 `:4905`: "Documented convenience wrapper — spec keeps `delete{ripple:true}` as canonical"). Why not client-side batch-composition (read `getTotalDurationTicks` → N explicit inserts): it costs an out-of-band readout round trip, N history entries (the precise divergence `insertBatch` was endorsed to kill), a TOCTOU race on the tail, and it inherits F1A-3's homogeneous-batch limit with no place to put the linked-companion law. **Sequencing:** the wire currently exposes only 2 of 5 strategies (`api.ts:42-50`), so the append strategy lands **with the r1 param-alignment wave** (15 `:4901` — "wire needs full PlacementStrategy + ripple + idSeed"); it slots as a row in the §4.1A routing-disposition table + §13.15 worklist. **The landed census is untouched by design:** today's 24 routed verbs + M49C gate + 6 exceptions (15 `:4893/:4897`) change nothing until the verb lands, at which point the census **re-declares mechanically** (D29 F8 tsc-lockstep: `WIRE_COMMAND_TYPES` fails typecheck until listed; coverage gate fails until routed or registered — "no spec amendment"). No engine work is required (Decision 12.3: OT's ops layer is the home; the engine's addClip stays INTERNAL transport).

### (d) Keyboard row (spec 16)

DaVinci's actual chord is **F12** (the Edit-page F-family: F9 insert / F10 overwrite / F11 replace / F12 append — fleet-researched, mode-replace `:175`, mode-ripple-overwrite `:282`). **Spec 16 grammar check:** zero F-key rows exist (mode-replace `:49` — the family is unclaimed), so no *internal* conflict — but F-keys are **browser-hostage** (F11 fullscreen / F12 devtools), the corpus's own researched precedent (r20 doc §2.4: "F-keys are browser-hostage — F11 fullscreen"). The task's suggested alternates: **`End` is TAKEN** (16 `:149`/`:151` — `Cmd+Right`/`End` = seek-to-end, also owned by both port keymaps; an append-on-End would double-bind and semantically entangle the playhead the mode must ignore) — reject, noting the free user chain "End (seek) then append (ignores it)". **Plain `D` is free** (16's single-letter census `:133-184/:212/:225-227/:297` = J K L I O V B H Z T Y U R N F S Q W M; no D, no E; ⌘D = duplicate `:244`) but FCP assigns D = overwrite (r20 `:180`, E/W/D for append/insert/overwrite) — conceptually colliding with the corpus's `.`-overwrite family. **Recommendation:** land the chord **family-shaped** with the mode cluster (the F12 block per mode-replace R5, with 16 §6.3's F-key browser-hostage rule) **or**, if the F-block is rejected, the fallback is **source-mode-gated plain `E`** — FCP's append key, free in 16 §3, in the variants' 56-row map, in nle-ui's 53-row map, in the OT 28-row port map, and in the mini's useKeys (grep-verified, zero hits) — context-disjoint from everything, riding the same source-mode gating mechanism as `,`/`.` (R20-W2 C46; 16's multi-descriptor contextPredicate law `:1516/:1518` supports it natively). Either form needs: a §3 binding row + Appendix-A `kbd-*` row + cheat-sheet row (the exact G5 pattern mode-insert filed for `,`/`.`), and the **D30 R5 lesson**: coordinate the key across the port keymap *and* the shell yield-sets in one lockstep commit — a source-mode-gated key is context-disjoint, so it dodges the double-fire class, but the row must still be registered as a deviation if 16 keeps `,`/`.` slip outside source mode.

### (e) UI affordance (spec 18)

1. **Media-pool menu gains "Append at End"** (clip-card context menu, §4.9's command-backed row rule): → `insert {placement:'append'}`; and with a pool multi-selection active, the row becomes **"Append N Clips"** — the mode card's "all at once" sentence gets its only possible home (pool multi-select already exists in 18 §4.2 `:146`, shift/cmd-click). Multi-select append is currently *nowhere*, not even mocked.
2. **Drag-to-end snap (the drag law extension, 18 §4.2 `:146`):** today a pool drag resolves `insertElement` at the pointer — dropping past the last clip leaves a **gap**. Law: when the drop x is at/beyond the hovered track's content end (or within the snap threshold of the tail, snap toggle N gating), the placement resolves `append` — the drag ghost snaps flush to the tail and the commit is gap-free. This converts "closest = dragging to the end" (scout-app row h) from an accident into a law.
3. **Source chrome:** the 7-mode SourceEditBar contract (the C46 ruling the variants already implement) gains its append button — icon verbatim from r20 §1.1 (`:56-63`: gray back-clip + white front + chevron), `data-tip` = the card's description; one-shot, no persistent mode, stays in source mode after fire (r20 §2 PROPOSAL 3/6).
4. **Preview grammar (the ghost/arrow tokens, r20 §1.3):** dashed ghost at the resolved tail + ghost-centered white down-arrow; **right-arrow forbidden** (only insert/ripple may show it, r20 `:125`); playhead untouched.
