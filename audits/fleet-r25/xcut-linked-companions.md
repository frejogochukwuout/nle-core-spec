**Method note on "law":** STATED-AS-LAW = a normative, mode-crossing statement of companion fan-out semantics that a port could be validated against. DIVERGENT = the homes disagree with each other or with DaVinci, or the behavior exists in no home at all.

**The default: coherent INSIDE the engine — `options.linked ?? true` at 15 sites (16 methods; one delegates). Default TRUE everywhere.** Every method that can touch a clip can fan out to its linked group, and callers must opt OUT with `{linked:false}` — which is exactly what every test fixture does (the mode-insert report's live-probe note: all 4 vitest pins + milestone 7.6 use `linked:false` or unlinked fixtures — the default path is the untested path).

**Supporting machinery (two companion predicates + one split law):**
- `getLinkedItemsForEdit` :729-737 — the WHOLE linked group (`findLinkedClips` :1460-1483 — modern `linkedGroupId` OR legacy originId+sourceId+position inference). Used by split/trim/ripple/roll/delete/move/insert/overwrite.
- `getSynchronizedLinkedItems` :751-767 — only companions sharing the anchor's EXACT `from/durationInFrames/sourceStart/sourceEnd/speed`. Used by slip/slide/rate-stretch. **This is a real, unstated semantic fork:** a linked companion with a different window is INCLUDED in trim fan-out but EXCLUDED from slip fan-out ("desync-safe by exclusion", mode-slip §4). Coherent design, zero spec text.
- `relinkSplitSegments` :668-690 — the split relink law: ≥2 linked clips split together → TWO fresh `linkedGroupId`s (lefts and rights); ONE linked clip split → the original group id is preserved on BOTH halves (the insert defect's root cause — the single-split half-set stays group-linked, so the left half rides the insert's shift expansion).

**The incoherence flags (cross-family):**
1. **Naming — three vocabularies for one concept.** Engine: `options.linked`. Wire: `params.syncLinked` (15 §4.3.2/:492-496, §4.3.5/:626-629, §4.3.6/:659-660, §4.3.7/:696-697 — the trim family only, 4 of 78 commands). App seam: no param at all — a view-level store toggle (`useUi.getState().link`, engineService.ts:236-248) gating the `av-link` id-closure. FreeCut itself used a global `isLinkedSelectionEnabled()`; the engine moved that gate per-call, and the app re-introduced it globally. The wire's DeleteCommand (§4.3.8 :706-731) and InsertCommand (§4.3.9 :738-759) have NO linked param although the engine's `removeItems`/`performInsertEdit` both take one — the two ends of the same seam disagree about which ops even have companion semantics.
2. **Default — one family member is recommended to break rank.** `performReplaceEdit` (mode-replace's proposed law) would land `{linked:false}` — the ONLY default-false member — because replace's semantics are SEVER-the-pair. That is correct for replace, but the corpus nowhere explains why insert/overwrite fan out by default while replace severs; a port author reading the engine alone would default everything true (and the naive `removeItems`+overwrite composition does exactly that — mode-replace §b trap 3).
3. **Model shape — pairwise vs group.** 09 §3.1A B1 (:155-158, :335): `ElementJSON.linkedTo?: string` — ONE companion, "the `linkGroupId` alternative was REJECTED." The engine: `linkedGroupId` — arbitrary N-clip groups. The app bridges neither to the other (the app's edits go through OT ops + the av-link closure over the pairwise `linkedTo` sidecar; the engine's `linkedGroupId` machinery lives on its unwired FreeCut-port side). 00:330 already directs the convergence ("Transitions/linked-groups/sync-lock take SceneTracks shapes per specs 06/07") — unexecuted.
4. **Split inheritance — two split-link laws in the corpus.** Engine/06:587/06:2180 (FreeCut split-bookkeeping :37-51): pair split together → lefts linked, rights linked (both halves stay paired, fresh ids). Mocks + nle-ui R14 (variants useUiStore :2051-2054, insertPlan :439-453; nle-ui :776-780): the right half SEVERS `linkedTo` entirely; only the left keeps the pair. 5. **Gating layer — selection-time vs dispatch-time.** The canonical UI path (OT `buildMoveGroup`, group-move.ts:169-201) takes a caller-supplied `selectedElements` list with ZERO link expansion in OT src (grep: no `linked|companion` matches in `src/lib/timeline/ops/`); the pair enters the op only because 05 §12.3 selection (`pairOf`, nle-ui useUiStore.ts:513-532, gated by the link toggle) put both ids in the selection. Three different layers claim the same responsibility; the nle-ui store is explicit that moves do NOT follow links ("sync-lock is 06 §6, a seal item — never claimed", :516-521) — which DIVERGES from the engine's `moveItems` default-true expansion.

## The law proposal

**Where the law lives (recommendation, in the corpus's own framing):** **spec 06 gains a cross-op section — §5.0 "Linked-companion propagation (the A/V link fan-out law)" — placed before the per-op §5.x sections.** The corpus has already voted for this home four times: 06 owns op semantics; 06 §13's per-op table already carries the seed column ("Multi-select?" — "Yes (synced linked)" / "Pair + linked counterpart pair" / "Anchor + linked counterpart + neighbors", :2971-2997); 06:3009 already states the one existing invariant row ("Linked companions move together"); and 06:3401-3404's property test already gestures at "cascade-required companions." The other homes keep their slices: **09 §3.1A B1 stays the MODEL home** (the `linkedTo` field — pending the group-shape reconciliation, XC-7), **05 §12.3 stays the SELECTION home** ("selecting one selects both"), **15 gains the param on every mutating command under ONE name** (see below), **18:202 (N4) stays the VIEW-GATE home** (link-OFF gates both selection propagation and companion fan-out, view-level, never editing doc-level links).

**The law's text (assembled from the corpus's own best fragments — the av-link seam's SEAM LAW is the single best existing statement, av-link.ts:10-24):**

> **§5.0 Linked-companion propagation.** When an edit targets an element whose linked companion exists (09 §3.1A `linkedTo`; engine `linkedGroupId`), the companion RIDES THE SAME OP: one command, one history entry, one ⌘Z. Propagation is an ID-CLOSURE EXPANSION applied BEFORE the op (symmetric over the link relation; live ids only; order-stable; cycle-free — av-link.ts:26-37). The op then applies its per-mode fan-out semantics per the table below. A companion on a LOCKED track never enters the closure (the explicit target's op gate owns rejection — av-link.ts:141-151). A companion on a SYNC-LOCKED track takes §6's interval/gap propagation INSTEAD of link-following (06:1825-1837 — the precedence rule). **Default: propagation ON (`syncLinked: true`); callers opt out per command.** Sync-lock (06 §6 — TRACK-level, `TrackJSON.syncLock`, propagates to whole tracks) and linking (THIS section — CLIP-level, `ElementJSON.linkedTo`, pairs one clip with one companion) are different mechanisms and are never conflated: linking answers "which clips move with this clip"; sync-lock answers "which tracks ripple when this track ripples."

**The fan-out table (the §13 "Multi-select?" column promoted to normative rows — every mode × every companion situation):**

## The no-overlap violation

**00-master-spec.md:804 (§13.5, property-based Tier-1 tests):** "No overlaps on any track after ripple/move/insert."

**The violation — CONFIRMED, live-probed by the mode-insert audit (/tmp vitest against the real `Timeline` class, engine tree clean):** `performInsertEdit(V1, m, 150, 0, 50)` over a linked pair — video S `[100,300)` (group G) + audio A `[100,300)` (group G) + downstream D `[300,400)` — with the DEFAULT `linked:true` yields V1 = `[150,200) S-left` + `[150,200) NEW` + `[200,350) S-right` + `[350,450) D`. **The left half occupies the same span as the inserted clip — a direct, exact overlap on the video track**, violating 00:804's letter for the insert op; the audio companion shifts whole to `[150,350)` unsplit, so the pair's junctions also desync at the insert region (a violation of the link law this audit proposes). The unlinked baseline is exact (`[100,150)+[150,200)NEW+[200,350)+[350,450)`, `hasOverlap(after)===false`).

**Why no test caught it:** the engine's 4 insert vitest pins + milestone 7.6 all use `{linked:false}` or unlinked fixtures; 00:811's Tier-1 edge case ("ripple across multiple tracks with linked clips") was never built anywhere; 06:3401-3404's `multi-select-op-consistency` property leaves "cascade-required companions" undefined. The corpus wrote the invariant (00:804), wrote the linked family (this audit's §2), and never ran them against each other.

**The fix's spec-side row (the §5.9B insert-edit law, companion clause — to land with mode-insert G1/G2):**

> **§5.9B Insert-edit (the DaVinci splice) — linked-companion clause.** A mid-clip insert on a track whose straddler is linked expands per §5.0: (1) the companion straddler on the paired track splits at the SAME insert frame (frame-aligned pair); (2) both split events relink with fresh left/right group ids (≥2 linked splits — `relinkSplitSegments` law); (3) the shift set is resolved PER HALF: the left halves of every linked group NEVER shift (they precede the insert frame); the right halves, their companions, and all downstream clips shift by the inserted duration on EVERY pair track; (4) postconditions — `hasOverlap === false` on every track (00:804), the audio junction equals the video junction at the insert region, and the edit is ONE undo entry. Engine-side acceptance (G2): a vitest pin with a linked mid-clip straddler asserting all four postconditions — currently the exact case that fails.

## Verdict

**NO LAW — seven fragments, ten private dialects.** The corpus's A/V-link semantics are the best example in the fleet of "specified as quotation, governed by nobody": 05 §12.3 states the SELECTION law ("selecting one selects both"); 09 B1 states the FIELD (`linkedTo`, one companion, groups rejected); 18:202 states the GATE (view-level link-OFF); 06 states per-op companion steps ONLY inside verbatim FreeCut algorithm quotations (roll's `keepTightestDelta` pair clamp, slip's companion fan-out, slide's counterpart+neighbors) plus a §13 census column and ONE invariant row (:3009 "Linked companions move together"); 15 states a param on 4 of 78 commands; and the single best statement of the whole idea — "the linked partner rides the SAME op, one history entry, one ⌘Z" — is a doc-comment in the engine's bridge (av-link.ts:10-24), covering only 5 ops, on a sidecar (`linkedTo`) the engine's own Timeline class doesn't use (`linkedGroupId`). Nothing cross-references anything: a port author cannot assemble the intended behavior from any single spec, which is exactly why the ten modes' implementations diverge.

The engine is the only complete implementation and is internally coherent on the default (`options.linked ?? true`, 16 methods) — but incoherent in quality of fan-out: trim/ripple clamp the group centrally (tightest δ), roll delegates re-clamping (junction desync), overwrite cascades removals but not survivor trims (asymmetric), insert fans out through a split that didn't relink (the 00:804 no-overlap violation, live-probed, unpinned, unqueued), and the two link predicates (whole-group vs window-synchronized) silently pick different companion sets for different modes. The app seam re-derives the law with a global gate and weaker clamps (per-element slip skip); OT — the Decision-12.3 algorithm home the whole family is porting INTO — has no link concept at all (zero matches in `src/lib/timeline/ops/`); the mocks carry a second, contradictory split law (R14 sever). Every mode does its own thing; the things disagree; and the one mode whose defect violates a master-spec invariant (00:804) proves the fragments were never run against each other.

The fix is cheap and the corpus has already written most of it: promote the av-link SEAM LAW + 06 §13's column + 06:3009's invariant row into one normative §5.0 with the fan-out table (§3 above), state the precedence (lock > sync-lock > link) and the naming ruling (`syncLinked` everywhere), land XC-2's engine fix before the r1 insert-edit port builds on the broken path, and add the one missing battery: linked fixtures into every op (XC-8). Until then, "linked" means one selection habit (05), one field (09), one wire flag (15), one store toggle (18), one seam comment (engine bridge), and ten different edit behaviors.
