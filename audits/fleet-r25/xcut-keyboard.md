### 2.2 Browser-hostage hazards (enumerated)

1. **F11 fullscreen** — Chrome/Edge/Firefox on Windows/Linux; the corpus's own citation (insert-modes.md:191: "F-keys are browser-hostage — F11 fullscreen").
2. **F12 DevTools** — same browsers; the muscle-memory key fights the *developer's* host habits.
3. **F1 help** — 16's own F1 contextual-help row (`:411`) makes the F-block's low edge adjacent to a live claim; some browsers bind F1 to help.
4. **macOS fn-defaults** — with "Use F1…F12 as standard function keys" OFF (the factory default), F9-F12 emit Mission Control / Show Desktop class OS functions and **never reach the page** — un-interceptable by any web shell (§8.4's non-US-layout concern, but worse: OS-level).
5. **Shift+F10 = the Windows/Linux context-menu key** AND our own 18 §4.9 normative route (hazard 2.1 above). A binding here must `preventDefault()` on keydown **and** the `contextmenu` event (mode-ripple-overwrite:286-287 got the browser half; the 18 half is new).
6. **The preventDefault law** (corpus precedents): 18:293 states the pattern in law ("`preventDefault` is mandatory so the browser page-zoom never fires" — the Cmd+wheel row); 16:30 proves the failure mode (capture-phase preventDefault in the port keymap does not stop the shell's window listener — the D30 R6 double-fire class). Any F-block row must (a) preventDefault at the shell's window listener, (b) ride the D30 R5 lockstep law (port keymap + shell yield-sets in ONE commit).
7. *One honest counter-weight:* F-keys are the most layout-stable keys (`event.code` = "F11" on every layout — §8.4's problem class doesn't touch them).

## The comma-period ownership

**The chain, traced end to end:**

1. **16's normative rows** (the canon): §3.4 `:232-235` — `,`/`.` = **slip ±1 frame (±4000 ticks), ⇧, / ⇧. ±10**, context "When clip selected, **slip tool active**"; §3.6 `:280-283` — `,`/`.` = **nudge** (plain `move`), "select tool active"; §3.4 `:250` + §6.1 row 2 `:591` — the disambiguation law: "**slip tool active → slip, any other tool → nudge**"; `:286-289` Option+ always-slip alts. (source mode)`", the comment: "R20-W2 (D2/C46): the source-viewer insert family — Premiere grammar, **gated to source-preview mode so the binding is context-disjoint from spec 16 §3.6's slip ladder above (registered deviation)**". Behavior twin `useShortcuts.ts:402-418`: `viewerMode === 'source' && sourceMediaId` → `insertMediaAt(sourceMediaId, ','?'insert':'overwrite')`; else → `slipNudge`.
3. **The app's wiring**: no source viewer exists — `,`/`.` reach `engineService.ts:388-404` (`case 'slip'`, one `updateElements` batch, engine-true) via nle-ui's `useShortcuts.ts:431-433` (unconditional slipNudge when a selection exists). 4. **The other documentary strand**: 05 §19 `:1496-1497` — "Insert edit (source → timeline) `,` / Overwrite edit `.` — **FreeCut only**" (comparison rows, not law); 16 §0 `:18` — the BASE note that the variants' map "adds ⌘5 + the source-mode `,`/`.` insert/overwrite rows, R20-W2 C46".

**Is there a real conflict?** **No — it is a context-split, and 16's own multi-descriptor law resolves it exactly as designed.** The source-mode rows and the slip ladder are context-disjoint: source-mode is a **viewer/panel context** (§6.2 step 3), the slip ladder is a **tool context** (§6.2 step 4) — step 3 outranks step 4, so in the source viewer `,`/`.` = insert/overwrite, and everywhere else the slip/nudge ladder holds untouched. §8.6 `:1516` makes the duplicate registration legal ("context-disjoint duplicates"), `:1514` provides the mechanism (`contextPredicate` — the variants' `viewerMode === 'source' && sourceMediaId` IS a contextPredicate, verbatim). The one thing the law *cannot* do by itself is invent the rows: **16 has no §3 row for the source-mode descriptors — the split lives only in a mock, a §0 BASE note, and 05 §19 comparison prose. The "ambiguity" is an unwritten-law problem, not a conflict.**

**The resolution (write it, don't re-decide it):** the family amendment's §3.4A lands the two rows as first-class descriptors on the same keys — `,`/`.` gain a THIRD and FOURTH descriptor each (`kbd-source-insert` / `kbd-source-overwrite`), contextPredicate = the C46 gate, listed BEFORE the slip/nudge descriptors per §6.2's order. §6.1 row 2 (`:591`) is amended from two meanings to three: "**source mode → insert/overwrite; slip tool (timeline) → slip; any other tool → nudge**". The C46 "registered deviation" entry in the variants' deviation register retires (ratified rows, no longer a deviation). 05 §19's `:1496-1497` rows get one cross-reference sentence (16 §11's table already reconciles 05 §19; these two rows join it). The nudge fallback for `,`/`.` never fires in the source viewer — and note the elegant corollary: the app, which has no source viewer, is untouched by the ruling (zero behavior change for every shipped surface).

## The slide trap

**Confirmed, from 16's own rows + conflict table:** §3.4 `:232-235` slip ladder (tool-gated) + §3.6 `:280-283` nudge ladder + `:250`/`:591` "any other tool → nudge". The slide tool (`U`, `:181`) is "any other tool" — **slide tool armed + `,`/`.` emits a plain `move {delta: ±4000}`**. A plain move shifts only the slid clip's `startTime`: it does NOT trim the neighbors, so it either overlaps them (00 `:804` global invariant: "No overlaps on any track after ripple/move/insert" — violated) or opens a gap — the exact anti-law of slide (06 `:2980`: "preserves total duration"; 06 §5.7's neighbor-trim law). The corpus's own mode-slide audit pins it (G2: "which breaks the 3-clip span invariant rather than sliding 1 frame").

**The variants' behavior makes it a third wrong answer:** `useShortcuts.ts:417` has no tool gate — slide tool + `,`/`.` **slips** (source window moves, box fixed — neither slide nor nudge). So all three surfaces (16's law, the variants' code, nle-ui's code) disagree, and none of them slides.

**The ruling: land slide-by-frame rows (mode-slide G2's option a), mirroring the slip ladder.**

- **Rows:** `,` / `.` (slide tool active, clip selected) → `{ type: 'slide', params: { elementId: <primarySelection>, delta: ±<frame-ticks> } }`; `Shift+,` / `Shift+.` → ±10. Appendix A: `kbd-slide-left-1` / `kbd-slide-right-1` / `kbd-slide-left-10` / `kbd-slide-right-10`.
- **§6.1 row 2 becomes four meanings:** source mode → insert/overwrite; slip tool → slip; **slide tool → slide**; any other tool → nudge. The multi-descriptor law carries it natively; the runtime-fps resolver (`:291`) applies unchanged.
- **Rationale:** (1) **Symmetry** — slip and slide are the corpus's own twin frame-level trim modes (the mock pairs their cursors; 05:972 detects them from pointer position; 16 gives them twin tool keys Y/U). A key that fires under the slip tool but does the *nudge* under the slide tool is precisely the class of trap §6 exists to close ("Every conflict is resolved explicitly"). (2) **The fallback breaks the corpus's own invariants** — a tool-gated key that silently violates 00:804 + 06 §5.7 is worse than no key. (3) **Explicit refusal (option b) is the wrong trade** — it would leave slide as the only selection-bound trim mode with no keyboard surface, and the keys still *fire* (refusal must be a real no-op row, which reads as a bug to users: same key, same selection, tool change → dead key). (4) **The roll precedent doesn't generalize** — mode-roll #7's "no frame-level roll nudge, registered, not accidental" is defensible because roll has no shared `,`/`.` key that fires under it (T is junction-bound pointer gesture); slide DOES share the key, so silence is not an option, only right-op vs wrong-op. (5) **DaVinci divergence is fine and cheap:** Resolve slides by keyboard via K+J/K+L (dynamic trim) — a grammar we CANNOT adopt (16 `:142-143` already owns K+J/K+L as half-speed playback), so our `,`/`.` mirror is a conscious divergence, same family as the T/Y/U/R radio divergence (§ below).
- **Carrier note:** the fix rides G-SLIP-5's tool-gate change (one gate, one descriptor array — nle-ui gains tool dispatch on `,`/`.` at the r1 keymap sync; the variants' `useShortcuts.ts:417` gains the same gate; both currently un-gated).
- **The 3-clip law applies verbatim:** slide-by-frame uses the same op as the gesture (`slideItem`/`SlideCommand` — one history entry, neighbor trims, span preserved); at track edges / missing neighbors, the op's own refusal path (non-adjacent → no-op per the mode-slide G7 ruling) governs — the key row needs no new law.

## The tool-vs-source-edit boundary

**16 §3.2's radio (verified):** `V` select / `B` razor / `H` hand / `Z` zoom / `T` roll / `Y` slip / `U` slide / `R` ripple-tool (+ `Esc` back-to-select, `N` snap, `Option+R` ripple MODE per the A6 resolution `:191`; + the FX tool, no plain key, R23-WA `:193`). 18 §4.5 `:198` mirrors it as the nine-tool radio (adding rate-stretch, toolbar-only). The set covers every **trim** mode as a *pointer gesture* state — `selectTool` view-state, one undoable drag each.

**The design boundary (correct, and currently IMPLICIT):** the DaVinci edit-mode family — insert / overwrite / replace / append / ripple-overwrite / fit-to-fill — are **not tools and must never join the radio**. They are **one-shot source-edit ops** driven from the media pool + the source-mode surface: the R20 research is explicit (insert-modes.md §2 PROPOSAL 3: "**NO persistent mode, NO radiogroup** (would imply a modal editing state that no NLE has)… One-shot action buttons"), the variants' SourceEditBar implements it (one-shot, acts on `sourceMediaId`, stays in source mode after fire), and DaVinci's own layout agrees (the edit-overlay strip under the SOURCE viewer, one-shot; my re-research confirms: the family fires from the source monitor's overlay/keys, while the toolbar's A/T/W/B tools are pointer modes). The corpus states the trim half of the boundary everywhere (16 §3.2 + 18 §4.5 inventories) but **no spec row states the other half** — that insert-modes are excluded from the tool enum. The boundary is carried only by: 15 §4.3.45's tool enum (closed list, no insert members), 18 §8.5's dual-viewer deferral (the source surface itself is v2), and the unratified C46 mock. The C45 "edit functions" subsection (insert-modes.md:306) is the filed-but-unactioned home for the op side.

**DaVinci's own trim/tool keys (re-researched live — the brief's "W ripple / R roll" is not what the sources say):** Resolve's default Edit-page grammar is a **single multi-mode trim tool**: `A` arrow/normal edit · `B` blade · `Cmd+B` razor · `T` Trim Edit (one tool — roll/ripple/slip/slide resolved by **pointer zone** over the clip edges/body) · `S` toggles slip↔slide inside trim · `W` dynamic-trim mode (sources also list Q/W as trim-start/trim-end to playhead; the pairs coexist in different presets) · `,`/`.` slip by frame once slip is active (Blackmagic forum: "Shift+V to select the clip, 't' to enter trim mode and (if necessary) 's' to toggle to slip from slide. Then use the ',' and '.' keys"). **There is no R-tool and no W-ripple in Resolve's default set.**

**So ours diverges by design, on three counts, two documented, one not:**

1. **One key per tool vs DaVinci's single-tool+pointer-zone dispatch** (T roll / Y slip / U slide / R ripple). By design — FCP-shaped (16 §11: "FCPXML is our handoff target — FCP muscle memory takes precedence"), and 18:198 already records one instance of exactly this choice (the DaVinci mock's A/,/S letters "corrected to 16 §3.2's V/Y/U"). The divergence itself is **undocumented** — no row says "Resolve collapses the trim family into one pointer-zoned tool; we use one-key-per-tool, deliberately." That note belongs in §3.2's reconciliation block.
2. **The R-key** (ripple TOOL vs `Option+R` ripple MODE, A6 `:191`) — our invention (Resolve has no ripple tool key; classic has the flag). Documented in law, but with the live two-world divergence still pending (16 `:30` D30 R6: OT + the app port bind plain `r` = loop-set; mode-ripple-trim G6 wants the two-world note in the R-row).
3. **Q/W** — 16 §3.4's split-side deletes (Q/W) vs Resolve's trim-to-playhead pair; ours rides `[`/`]` + ⌥[ / ⌥] for trim-to-playhead instead. Divergent, undocumented, but harmless (no shared claimant).

**Ruling:** the family amendment adds ONE boundary sentence (16 §3.4A preamble, mirrored in 18 §4.3's C46 ratification): "*The source-edit family is not part of the tool radio — no `selectTool` member exists or is planned for insert/overwrite/replace/append/ripple-overwrite/fit-to-fill; they are one-shot source-mode ops fired from the source-edit bar or the §3.4A keys. The tool radio remains pointer-gesture state (the trim family's V/B/T/Y/U/R).*" + a closure note on 15 §4.3.45's enum (the union must not gain source-edit members) + the §3.2 DaVinci-divergence note above. This converts the boundary from implicit to law at the cost of three sentences.

## Verdict

The DaVinci edit-mode family's keyboard surface is **canon-empty by omission, not by conflict**: the F9-F12 block is genuinely unclaimed (16+18+00, grep-zero), every letter the family needs is free where it needs it (`E`, `Shift+.`), and the one live internal claimant the fleet missed — **18 §4.9's normative Shift+F10 context-menu route** — is avoidable by re-chording ripple-overwrite rather than fighting it. The `,`/`.` "conflict" dissolves under 16's own multi-descriptor law (§8.6:1516/1518) + §6.2's context order: source-mode is a panel context (step 3) that legitimately outranks the slip ladder's tool context (step 4) — what's missing is not a decision but the two §3 rows the variants have been implementing (and testing) since R20-W2; ratify them and the C46 deviation dies. The one genuine spec defect is the **slide trap**: 16's own disambiguation ("any other tool → nudge") makes `,`/`.` under the slide tool a span-breaking plain move — a violation of 00:804 and 06 §5.7 written into the conflict table itself — and the fix is the ladder's own symmetry (slide-by-frame rows, four-meaning §6.1 row 2). The tool radio is complete by design and the boundary is real (source-edit modes are one-shot ops, not tools — DaVinci's own architecture), but the boundary is implicit everywhere; three sentences make it law. The DaVinci tool-key divergence is real (Resolve: one pointer-zoned trim tool + S toggle; ours: one key per tool, FCP-shaped) and by design — documented for the R-key (A6), undocumented for the rest. **Disposition: one family-shaped amendment, two tiers — primary source-mode-gated chords (`,`/`.`/`Shift+.`/`E`), F-block as documented DaVinci-parity alternates with the preventDefault + hostage law — plus the slide rows, the §6.1 amendment, and the boundary sentence; XKB-1 ratifies now, everything else lands with the r1 verbs under the D30 R5 lockstep law.** No repo modified; no commit; sole write = this report.
